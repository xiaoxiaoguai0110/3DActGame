## 今日讨论要点

### 1. 输入系统的架构设计

**讨论问题**：新 Input System 的输入处理应该怎么组织？

**结论**：采用 **InputReader 单例 + 混合模式**

| 输入类型 | 处理方式 | 原因 |
|----------|----------|------|
| **移动（WASD）** | 每帧读属性 `MoveInput` | 持续输入，值变化不频繁但使用频繁 |
| **攻击/跳跃/格挡** | 事件驱动 `OnAttack` | 瞬时输入，一次性触发即可 |

**工程感悟**：
- 移动和跳跃是两种不同类型的输入，适合不同的处理方式
- 不要一刀切全部用事件或全部用轮询，要看场景

### 2. 单例模式（MonoBehaviour 版）

**核心模板**：

```csharp
public static ClassName Instance { get; private set; }

void Awake()
{
    if (Instance != null)
    {
        Destroy(gameObject);  // 已有老大，新来的滚蛋
        return;
    }
    Instance = this;
    DontDestroyOnLoad(gameObject);
}
```

**关键理解**：
- `if (Instance != null)` 判断是为了防止场景切换时重复创建
- 销毁的是**新来的**，不是旧的，保证已有引用不会断
- `DontDestroyOnLoad` 让这个对象跨场景存活

**面试考点**：
- 单例的优缺点
- 为什么不能直接 `Instance = this` 覆盖
- 多线程环境下单例的线程安全问题

### 3. 组件概念

**核心理解**：
- Unity 中挂载到 GameObject 上的每一个脚本/功能块都是**组件**
- `MonoBehaviour` 继承类 = 组件
- 组件化的好处：一个 GameObject 可以有多个组件各司其职

### 4. 事件驱动 vs 每帧轮询的性能误区

**核心结论**：两者性能差距可以忽略不计

- 事件：**只在值变化时触发**，按住 W 不放只触发一次
- 轮询：`ReadValue<Vector2>()` 本质是读缓存，开销极小
- 选择依据应该是**代码清晰度**和**控制权**，而不是性能

## 2026-06-11 Trigger 碰撞检测的 Rigidbody 坑

### 问题描述

玩家的剑上挂了 Trigger Collider，但只能检测到 Player 自己，检测不到怪物。即使 Collider 线框和怪物的 Collider 明显重叠，`OnTriggerEnter` 也不触发。

### 排查过程

1. ✅ 剑的 Collider 已勾选 `Is Trigger`
2. ✅ 怪物有 Collider 组件
3. ✅ 两个物体 Layer 都是 Default（碰撞矩阵正确）
4. ✅ Collider 在 Scene 视图中的线框确实重叠
5. ❌ `OnTriggerEnter` 只输出 `碰到了 Player`

### 根因

**怪物身上没有 `Rigidbody` 组件。**

Unity 的 Trigger 碰撞规则：
```
Trigger Collider → Collider（无 Rigidbody）→ ❌ 不触发
Trigger Collider → Collider（有 Rigidbody）→ ✅ 触发
Trigger Collider → CharacterController → ✅ 触发（特殊处理）
```

剑能检测到 Player 是因为 Player 用 `CharacterController`（内部自带物理处理），而怪物只有 Collider 没有 Rigidbody，所以永远不触发。

### 修复方案

在剑上加 **Rigidbody**，勾选 **Is Kinematic**（不受物理影响、不下落），取消 **Use Gravity**。

### 教训

- **做 Trigger 碰撞检测时，至少要有一方有 Rigidbody/CharacterController**，这是 Unity 物理系统的硬性要求
- 如果检测不到触发，先检查双方是否都有物理组件（Rigidbody / CharacterController），而不是只盯着 Collider 大小和位置
- 不要因为一方能触发（剑碰到 Player）就默认另一方（剑碰到怪物）也没问题，底层机制可能不同
